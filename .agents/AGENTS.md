# AGENTS.md - 项目规则与长期记忆宪章

---

## 🏛️ 第一部分：核心人机协同底座 (Core Meta-Collaboration Engine)
> **适用范围**：全语言、全技术栈、全项目通用。定义人机协作最底层的边界、原则与交互标准。

### 1. 人机协同与执行边界契约
- **语言原则**：思考过程使用英文；最终输出、文档（如 `SESSION_HANDOFF.md`、`architecture_design.md` 等）及交互解释统一使用简体中文。
- **执行边界**：严禁 AI 自行运行代码、构建黑盒测试脚本或擅自启动项目服务，由用户担任唯一的系统执行者与物理测试者。
- **版本管理与代码校验时机**：
  - 日常编码、样式调整或连续交互期间**严禁频繁递增版本号与反复执行 Git Diff 校验**，保持交互轻量高效；
  - 仅在用户显式发出“提交”（或 commit）收尾指令时，由 `git-commit-suggestion` 技能统一执行物理代码差异核准（Git Diff Verification）；
  - **版本递增精细化**：仅在包含功能演进或缺陷修复时集中递增工程最低位版本号（SemVer Patch 号或第 4 位构建号）；纯文档维护（`docs`）或纯工作流维护（`chore(workflow)`）**严禁递增版本号**；若项目配置了 CI/CD 自动化发版，则免除物理递增。
  - **版本号用途**：用户通过启动横幅 `SerialSync Launcher vX.Y.Z` 对比双端版本号，确认代码一致性。
- **Git 工作流与提交指令触发**：不要自动执行 `git commit` 或 `git push`。日常代码变更或微调时无需主动输出提交注释建议；仅在用户显式发出“提交”（或 commit）收尾指令时，由 `git-commit-suggestion` 技能统一梳理全量差异并生成中文提交注释。
- **Git 提交注释输出规范**：用户偏好使用图形界面（GUI）管理 Git。在提供提交注释建议时**仅提供纯文本代码块（```text ... ```）包装的提交注释内容**，**严禁附带任何 `git add` 或 `git commit` 等命令行控制字符**。
- **收尾交付不越权原则**：阶段收尾与提交归档时，**严禁在回复末尾附带任何诱导性待办建议或擅自规划下一步开发**，保持交付纯粹，完全由用户下达下一步指令。
- **反馈闭环**：当用户反馈测试结果或报错时，先深入分析根因与逻辑差异，给出明确的修改计划，在获得用户确认后再执行代码变更。
- **代码风格**：遵循当前技术栈最佳语言规范，注重代码可读性、可维护性和执行性能。避免过度设计，保持代码简洁明了。

### 2. 架构设计与反过度工程化铁律 (KISS & Anti-Over-Engineering)
- **避免过度工程化 (Anti-Over-Engineering)**：优先寻求语言标准库与框架原生态干净解法，严禁动辄引入重型第三方库、复杂黑盒补丁或非必要的抽象层。
- **连续失败警停机制 (Circuit Breaker)**：若一种方案连续两次无法解决问题，**必须立即停止“叠加补丁”**，回归第一性原理重新审视模块整体架构与数据流向。
- **自编组件/自建工具适用原则 (Component Attributes Priority vs Internal Logic)**：在适用或排查自定义公共组件相关问题时，必须先检查该组件暴露的外部配置与属性是否足以解决问题；只有在现有配置无法满足或确属底层逻辑缺陷时，方可改动基础组件自身内部逻辑，避免轻率修改底层导致牵一发而动全身。
- **彻底重构与旧代码边界**：重构项目是对旧系统的全面升级，旧系统代码仅作为理解业务意图与需求边界的参考，严禁盲目依赖或照搬旧代码的不规范设计。从实际业务需求与现代工程最佳实践出发。
- **即时沟通确认**：遇到任何业务设计疑虑或模糊需求时，必须即时向用户提出讨论，严禁自行凭空假设。

### 3. 用户操作反馈与交互体验铁律 (Feedback & Confirmation UX Standards)
- **成功操作静默响应**：数据保存、修改、删除成功后**严禁弹出打断操作流的确认框/弹窗**（如“保存成功”、“修改成功”），统一采用无感状态机（如按钮自动置灰、列表局部静默刷新、状态栏轻量提示）进行静默响应。
- **长耗时后台任务模态等待进度规范**：对批处理、数据清洗迁移、全量导出等长耗时（>1~2秒）操作，严禁卡死主线程/UI 或让用户无提示等待；统一采用全局模态等待窗体/加载遮罩（提供动态阶段提示与进度反馈），执行完成后静默自动关闭。
- **破坏性操作安全拦截**：数据删除、清空、或放弃未保存修改等具有破坏性或不可逆的操作**执行前**，必须明确弹出对话框向用户进行二次确认，确认后方可执行。
- **UI 界面微调保护原则 (Respect User Visual Edits)**：当用户在可视化设计器（或前端布局文件/CSS）中手动微调了尺寸、坐标、字体、颜色、边距等视觉细节时，AI **严禁在代码编写或重构中武断改动、重置或模板覆写**这些视觉微调结果，全量尊重并保留用户微调成果。

### 4. 文档唯一性与状态单一真理源 (Single Source of Truth)
- **静态规则唯一真理源**：本项目宪章 `AGENTS.md`。仅固化长期通用协作契约与架构铁律，**严禁在本文档中登记动态任务或临时资产清单**。
- **动态状态唯一真理源**：`docs/SESSION_HANDOFF.md`。全系统**唯一的跨会话动态上下文交接中枢**（承载当前核心攻坚主线、版本基准、最新已就绪核心资产、以及历史交接流水）。
- **系统技术全景唯一大账本**：`docs/architecture_design.md`。承载长期技术选型、核心数据模型、分层架构与全局 Backlog 清单。
- **规则升华准入门槛 (Rules Elevation Threshold)**：
  - 日常业务逻辑开发与常规功能增删改查**严禁盲目向本文件追加规则**，坚决杜绝 Prompt 膨胀与注意力稀释；
  - 仅当发生“重大架构推翻重构”、“严重连续性踩坑/死锁”或“抽象出跨模块通用底层契约”时，方可提炼升华；
  - 升华时必须优先合并、精简既有条款，保持全局宪章高度紧凑凝练。

## 🗄️ 第二部分：企业级业务与持久层架构拓展包 (Domain & Persistence Extensions)
> **适用范围**：业务系统、数据服务及包含持久层/数据库的项目。纯算法、CLI 工具或轻量前端项目可按需裁撤。

### 5. 业务逻辑零硬编码与单一真理源 (Strict No-Hardcoding & Single Source of Truth)
- **严禁业务逻辑硬编码 (Zero Hardcoding Tolerance)**：全系统严禁在业务逻辑代码中硬编码业务分类、权重排序、风险评级、颜色映射、或关键字模糊推导等猜疑逻辑。
- **配置与数据字典为全局唯一真理源**：
  - 业务分类属性、优先级、状态映射等，100% 遵从数据字典（如 `data_dictionary` 表、配置文件或集中枚举元数据配置）；
  - 系统具备完全的动态可配置能力，未定义项采用通用缺省值，严禁在代码中擅自根据字面臆测。

---

### 6. 数据生命周期与全系统软删除规范 (Database Lifecycle & Unified Soft Delete)
- **全系统软删除规范 (Unified Soft Delete)**：所有核心业务实体/表全线统一采用软删除标准，字段统一定义为 `is_delete`（0: 正常, 1: 已删除）。业务删除统一执行软删除标记，严禁物理硬删除（`DELETE FROM`）。
- **生命周期自然终结 vs 系统软删除 (Lifecycle End vs Soft Delete)**：
  - **客观事实终结**：业务关系的自然终止（如员工离职、用户注销、租约到期、合同终止等）属于客观历史事实，必须通过状态字段（如 `status = 'terminated'`）和起止时间（`end_date`）表达，数据仍需在库呈现以供审计与历史追溯，**严禁将其标记为 `is_delete = 1`**；
  - **系统软删除**：`is_delete = 1` 严格且仅用于表达“录入错误 / 用户撤销 / 人工废弃”的脏数据场景，在日常业务查询与统计中对用户完全隐匿。
- **查询与索引一致性**：所有常规业务查询与数据排重逻辑必须显式过滤软删除记录（`WHERE is_delete = 0`）；核心高频查询的复合索引必须覆盖 `is_delete` 列。
- **数据库数据可读性规范 (Human-Readable DB Data)**：数据库中（包括常规关系列与 JSON 扩展字段）严禁存储不可读的 Unicode 转义编码（如 `\uXXXX`）。所有 JSON 序列化落地前必须反转义还原，确保直接在数据库管理工具中查看时全部呈现为人类可直读的原生态 UTF-8 字符。

### 7. 性能军规与防 N+1 规范 (Performance & Batch Priority)
- **消灭 N+1 循环查库与循环网络调用 (Batch Query Priority & Anti-N+1)**：在批量展示、台账导出或关联关系解析场景下，**严禁在循环（`for` / `foreach` / `map`）内反复执行逐条单行 SQL 查询或逐条远程 RPC 调用**；必须统一采用分批参数化（`IN`）批量查询契约，单次批量拉入内存并转换为 Hash Map 字典，在内存中完成关联映射。
- **高频交互工作集二级内存缓存 (Working-Set Memory Cache)**：对承载高频浏览、键盘上下键连续切行、或密集滚动的场景，必须在数据加载时对主档案及关键关联数据实施局部预热缓存；连续操作时 100% 内存直读命中；在数据增删改后精准执行缓存失效与重置。
