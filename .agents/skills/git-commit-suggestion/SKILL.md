# Git 提交与开发阶段归档工作流 (Commit & Session Archive)

本技能用于在用户发出**“提交”**、**“commit”**或相关会话收尾指令时，全面梳理本次会话/本阶段的全部开发成果，提炼关键原则与踩坑经验，**自动固化长期记忆与开发文档**，检查版本号规范，并生成高质量的纯文本 Git 提交注释。

---

## 核心执行流程

### 1. 统一物理代码差异核准 (Git Diff Verification) 与成果提炼
- **代码物理审查**：首先执行只读命令 `git status -s` 与 `git diff HEAD --stat`，全面梳理本次会话自上一次 Git 提交以来的**全部真实代码变更范围**（同时覆盖工作区 Working Tree 与 GUI 暂存区 Staging Area，涵盖业务逻辑、数据访问、API、前端组件、资源文件及配置等），核查是否有意外改动或换行符污染；
- **提炼开发要点与成果**：清晰概括本次开发解决了什么痛点、交付了什么具体功能或修复了什么缺陷；
- **提炼通用规范与开发铁律**：重点反思本次开发是否抽象出了**全局通用组件、沉淀出了可复用的架构模式、交互排版铁律或避坑经验**（例如：后台任务模态进度反馈、消灭 N+1 循环查库等）。

---

### 2. 集中递增工程版本号 (Unified Version Bump)
- **提交时统一递增**：日常代码微调或连续修改过程中**严禁频繁递增版本号**；在收到“提交”指令后，按以下精细化策略处理：
  - **递增条件与位级**：仅当本次提交包含核心业务演进（`feat`）、重构（`refactor`）或缺陷修复（`fix`）时，统一将对应工程元数据文件中的**最低位版本号向上递增 1 位**（遵循 SemVer 的 Patch 修订号或第 4 位构建号）；
  - **免递增保护**：纯文档维护（`docs`）或纯工程/工作流微调（`chore(workflow)`）**严禁递增版本号**，防止版本号通货膨胀；
  - **CI 兼容**：若项目声明接入了自动化发版（如 semantic-release / Changesets / Git Tag CI 流程），免除物理文件版本号修改；
  - **目标文件映射**：
    * Node.js 项目：`package.json` 中的 `"version"`；
    * Python 项目：`pyproject.toml` 或 `setup.py` / `__version__.py`；
    * Go / Rust 项目：`Cargo.toml` 或版本常量文件；
    * .NET 项目：对应工程的 `Properties/AssemblyInfo.cs` 中的 `AssemblyVersion` 与 `AssemblyFileVersion`。

---

### 3. 自动维护通用交接文档与长期记忆 (Memory & Docs Persistence)
在给出提交建议的同时，AI 必须主动完成以下唯一交接与记忆文件的同步更新：
1. **自动更新动态状态唯一真理源 [docs/SESSION_HANDOFF.md](file:///docs/SESSION_HANDOFF.md)**：
   - **业务代码演进 (`feat` / `refactor` / `fix`)**：
     * 更新顶部【当前进行中任务基准】中的当前攻坚主线与版本基准；
     * 将提交注释与核心资产写入【核心业务与功能最新里程碑 (Core Feature Baseline)】板块；
   - **纯工作流与文档维护 (`chore(workflow)` / `docs`)**：写入【最近一次工程与工作流维护记录 (Last Workflow Maintenance)】板块，**严禁覆写核心业务里程碑**，确保业务记忆永不丢失；
   - 在历史交接归档流水中追加一行本次交接简述。
2. **审慎升华长期规则至 [.agents/AGENTS.md](file:///.agents/AGENTS.md) (Rules Elevation with Safe Threshold)**：
   - **【升华安全准入门槛】**：日常业务增删改查或常规缺陷修复**严禁向 `AGENTS.md` 追加规则**，严防 Prompt 膨胀与注意力稀释；
   - **【仅限重大沉淀】**：仅在本次开发触发了“架构推翻重构反思”、“严重技术陷阱/死锁”、或确立了“跨模块全局通用契约”时，方可升华规则；
   - **【合并提炼原则】**：写入时优先合并、归纳或修订既有章节条款，保持 `AGENTS.md` 紧凑精炼，不堆砌碎片化微观业务逻辑。
3. **重大技术决策归档进 [docs/architecture_design.md](file:///docs/architecture_design.md)**：
   - 若本轮涉及重大架构设计、核心 API 契约或通用表结构变更，按规范追加至开发日志或更新 Feature Backlog。

---

### 4. 严格遵循 Conventional Commits 规范
- **标题行**采用标准形式：`<type>(<scope>): <简明扼要的修改主旨>`
  - `feat`: 新增业务功能、新模块或新接口
  - `fix`: 缺陷修复、SQL 字段缺失补全、异常报错处理
  - `style`: 样式视觉风格调整、格式化与排版对齐
  - `refactor`: 代码结构重构与性能调优（不改变外部功能表现）
  - `perf`: 性能提速与内存/并发优化
  - `chore`: 项目依赖、版本号递增、构建配置等
- **正文行**采用条理化的列表（`- ...`），逐项概括各层级的关键修改。

---

### 5. 输出规范与红线约束（绝对红线）
- **严禁提供下一步开发建议**：提交指令是当前开发阶段的收尾与归档。AI **严禁在提交回复中附带任何“下一步建议”、“后续施工推荐”或擅自规划后续工作**。后续任务安排完全由用户主导；
- **GUI 纯文本输出原则**：用户偏好使用图形化客户端（GUI）管理 Git，**严禁附带任何 `git add`、`git commit`、`git push` 等命令行控制字符或 Shell 命令代码块**；
- **纯粹交付**：**仅以纯文本代码块（```text ... ```）输出可直接复制粘贴的提交注释内容**，保持干净、利落、专业。
